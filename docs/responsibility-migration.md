# Sysal 与 SystemCard 职责和数据契约

## 定位与版本

Sysal 提供尽量详细、可复用的 Linux 系统信息，负责采集、解析、归一化、关联和证据状态。
SystemCard 根据终端用户的需要选择采集范围、重要字段和展示方式。
其他调用方应能直接使用 Sysal 的结果，无需借用 SystemCard 的设备识别和状态推断代码。

本契约适用于 Sysal 0.0.26 和尚未发布的 SystemCard 0.1.2。具体接口以公共头文件为准。
实施记录写入 Git，不维护逐日开发日志。

## 职责与依赖

| 事项 | Sysal | SystemCard |
| --- | --- | --- |
| 读取系统接口 | 实现只读后端，保留原始证据及失败原因 | 通过公共 API 请求采集 |
| 数据语义 | 设备分类、协议、能力、可见性、清单完整性 | 消费明确的事实和状态 |
| 采集选择 | 提供按领域与必要选项控制的能力 | 将栏目、概要和详情转换为采集计划 |
| 执行边界 | 权限、适用性、资源限制、可执行的超时和跳过原因 | 选择适合交互命令的配置 |
| 展示 | 提供类型化数据、JSON 和必要查询接口 | 取舍、排序、分组、单位、文案、颜色及布局 |

继续使用现有 `Reader → RawStore → Parser → Resolver → System` 管线。
来源解析归 Parser，跨域关系归 Resolver，JSON 保持领域拆分。
库所需的辅助采集由 Sysal 管理；卡片为了同时展示多个领域而产生的组合由 SystemCard 管理。

绑定层只使用 Sysal 公共头文件，转交领域和选项并转换结果。
卡片名称、`--compact`、`--section` 和终端宽度均属于 SystemCard。

## 职责分配

| 位置 | 迁移前 | 当前职责 |
| --- | --- | --- |
| `src/reader/linux/filesystems.cpp` | 按文件系统类别写死容量查询范围 | 分类与查询策略分开，调用者可明确选择查询范围 |
| `src/reader/linux/sensors.cpp` | 显示类 PCI 设备的传感器被隐式跳过 | 保留通用传感器能力，过滤成为显式选择并记录原因 |
| `include/sysal/types/enums.hpp`、`src/parser/storage.cpp` | `StorageKind` 混合 NVMe 协议与 SSD/HDD 介质，并依赖名称前缀 | 建立独立维度，优先采用系统明确报告的证据 |
| `SystemCard/src/systemcard/storage.py` | 判断整盘、光驱、介质和协议，并关联 SCSI host | 事实判断及关联归 Sysal；卡片保留展示筛选和计数 |
| `SystemCard/src/systemcard/cpu.py` | 解释特性别名，补推 SMT 支持 | Sysal 统一解释；客户端选择常用能力、标签和布局 |
| `src/parser/cpu.cpp` | 全局 `isa_extensions` 取自第一个逻辑 CPU | 明确逐 CPU、观察到的并集及共同项的语义 |
| `SystemCard/src/systemcard/collection_status.py` | `inventory_known()` 根据来源记录推断零与未知 | Sysal 为具体清单提供明确状态，客户端按状态展示 |
| `SystemCard/bindings/pybind_sysal.cpp` | C++ 绑定维护栏目到领域的映射 | Python 生成采集计划，绑定只转交通用参数 |

`SystemCard/` 在此表中表示同级仓库 `../SystemCard`。

## 数据契约

### 清单状态与有效零值

保留现有 `CollectStatus` 和来源观察。具体清单的完整性采用
`Unknown`、`Partial`、`Complete` 三种值。一个领域内不同清单分别判断，
例如逻辑 CPU、NUMA 节点和缓存不能共用一个未经区分的完整性标记。

| 结果 | 含义 |
| --- | --- |
| 清单为空且在声明范围内完整 | 可以确认该范围内为零项 |
| 清单为空但读取失败、未请求或完整性未知 | 数量未知 |
| 清单非空且不完整 | 已观察到的条目，数量为已知部分 |
| 清单完整但部分属性不可读 | 条目清单完整，属性继续保留未知 |

完整性只针对声明的来源、命名空间和采集范围，不保证看见整台物理机器的全部设备。
可选属性读取失败不能直接推翻设备枚举的完整性。
现有 `succeeded_collectors` 继续表示领域生成了结果，不能充当清单完整性的替代。

Reader 保留枚举是否完成的证据；归一化身份与枚举不一致时，不能确认清单完整。
Resolver 保留这些状态，并负责关联引起的局部缺失。SystemCard 不再扫描整个领域的失败记录来判零。

### 失败与跳过原因

失败仍使用现有 `ReadFailure`。`SkipReason` 区分未知、未请求、按策略排除、预算耗尽和接口不适用。预算耗尽为可表达的原因，当前未引入通用预算参数。
失败、未尝试、接口不适用和原因未知分别表达，避免客户端解析英文 `note` 来识别状态。
`note` 可保留补充说明，状态与原因采用类型化字段。

旧快照没有新状态时保留未知。成功的旧领域、空数组或当前默认配置都不足以补出历史完整性。

### 存储模型

保留已有设备号、分区关系、SCSI/NVMe 信息和原始 `rotational` 报告。
以下维度分别表达，具体枚举由可验证的来源确定：

| 维度 | 表达内容 |
| --- | --- |
| 块设备层级 | 整设备、分区、映射、RAID、loop 等内核关系 |
| 设备用途 | 磁盘、光学介质、其他或未知 |
| 旋转属性 | 内核报告旋转、非旋转或未知 |
| 访问协议 | NVMe、ATA、SCSI 等可证明的协议 |
| 传输方式 | 系统明确提供的 SATA、SAS、USB、PCIe、TCP、RDMA 等信息 |

归一化规则应保留证据的强度：

- NVMe namespace/controller 关系可证明 NVMe，名称前缀只保留为原始名称。
- ATA 端口可证明 ATA 关联，不能单独证明 SATA。
- SCSI 地址不能单独证明 SAS。
- 非旋转不能直接证明物理介质一定是 SSD，RAID 暴露的逻辑设备也不能代表全部底层磁盘。
- 未识别和缺少证据保留未知；其他客户端应获得同样的分类结论。

旧 `StorageKind` 在过渡期间保留，并明确其兼容用途；新模型及新客户端不再以它作为唯一分类依据。
SystemCard 的分类计数与标签以新事实为输入，保留“内核报告”和“已知部分”等范围说明。

### CPU 能力

保留每个逻辑 CPU 的完整内核特征、标识和来源。标准化能力标识与别名解释放入 Sysal，
常用项名单、可读名称和显示顺序留给 SystemCard。

能力状态至少区分已报告、未报告和无法确定。缺少内核 flag 不能直接成为“不支持”。
SMT 的内核支持状态、当前活动状态和实际线程拓扑继续分别表达，客户端移除重复的控制字符串推断。

公共查询需要明确：并集表示至少一个已观察到的 CPU 报告了该能力；共同项需要说明参与范围和证据完整性。
不能将第一个逻辑 CPU 的特性解释为全机保证。优先复用逐 CPU 数据，通过查询接口形成集合，
避免在快照中保存多份容易失去一致性的能力表。

### 文件系统与通用派生量

保留挂载别名关联、块单位、空闲和可用空间的区别、inode 及部分结果。
根文件系统摘要、隐藏伪文件系统的表格和显示百分比留在 SystemCard。

Sysal 保持文件系统视图与物理存储容量的区别。分类为未知不等于统计接口不支持；
查询范围和后端适用性分别判断。文件系统视图不提供未经验证的跨视图物理容量总和。
单位转换、简单显示计算和百分比排版可以留在客户端，输入事实及不确定性由库统一表达。

## 采集选项与生命周期

保留 `Collect` 位掩码。先采用少量类型化选项，覆盖文件系统容量查询范围和传感器设备选择，
不建立通用规则语言、插件调度框架或按界面字段编排的 API。

| 选项 | Sysal 的能力与默认值 | SystemCard 的选择 |
| --- | --- | --- |
| 文件系统容量 | 提供不查询、本地查询、明确请求更多支持类型的范围；默认本地查询 | 普通交互命令选择本地查询 |
| 传感器设备 | 通用能力包含系统已公开的显示类设备传感器；提供显式设备选择 | 按展示与开销要求选择，不要求库永久删除能力 |
| 原始证据 | 明确请求 `Raw` 时保留完整证据 | 普通展示不请求 `Raw`；`--sources` 使用元数据 |

默认的本地容量查询出于 I/O 阻塞边界。请求全部领域与启用额外查询分别控制。
自动挂载接口不能因一次信息采集触发挂载，任何模式均保持系统配置只读。

命令执行器现有的超时和输出限制继续保留。`statvfs` 等同步调用没有通用的硬超时保证；
远端查询扩展必须说明实际执行边界，后端不能满足约束时明确报告，不能把等待超时当作 I/O 已终止。
实现可验证的隔离边界前，不对全部系统调用承诺统一强制超时。

公共入口保留现有调用并提供重载：

```cpp
static System collect(Collect flags = full);
static System collect(Collect flags, const CollectOptions &options);
```

`CollectOptions` 提供 `FilesystemQuery::{None, Local, AllMounted}` 和 `SensorDevices::{All, ExcludeDisplay}`。
选项在采集前验证；`meta.collection_request` 和 RawStore 保存原始请求，`meta.requested_flags` 表达当前解析范围。
`refresh()` 沿用当前解析范围与原始策略；旧快照缺少请求时拒绝隐式刷新，调用方明确执行 collect。
源代码可继续调用旧入口；公共模型变化要求重新编译并匹配头文件与库。

`from_json()` 和 `collect_from_raw()` 保持纯数据恢复与回放，不因选项描述而发起新采集。
回放解析给定证据，不用当前默认策略删除已存在的记录；旧证据缺少请求选项时标为未知。
容量读取按描述符逐级检查 automount，拒绝符号链接和父目录跳转；不支持相应描述符接口的内核保留查询失败。
恢复采集由调用方明确调用采集或刷新入口。

## 客户端与绑定迁移

SystemCard 在 Python 中生成采集计划，集中维护栏目需要的领域与选项。
原生绑定接受公共领域枚举和选项，继续返回 JSON 兼容数据，不暴露 Sysal 私有 reader/parser。
领域常量来自 C++ 公共定义，Python 不复制位号。

绑定尊重显式的 `Raw` 请求，采集与 JSON 输出均保留原始证据。
SystemCard 普通采集计划不选 `Raw`，诊断来源与原始 payload 分开控制。

Python 负责的内容包括卡片取舍、分组排序、格式化、布局和着色，
以及 JSON 结构和数值的防御性读取。必要的旧数据兼容集中在一个适配边界；
卡片内不保留永久的旧语义推断后备路径。

## 模块边界与验收要点

Sysal 独立提供可用结果，SystemCard 消费公共接口。兼容字段集中隔离，
同一事实只保留一个权威的归一化实现。

| 批次 | 主要修改 | 完成条件 |
| --- | --- | --- |
| 一 清单状态 | `snapshot_meta.hpp`、reader 枚举证据、pipeline/serialization、客户端状态适配 | 零、部分清单和未知可由库直接区分；可选属性缺失不改变枚举结论 |
| 二 存储模型 | `storage.hpp`、parser/resolver/storage、领域序列化、`storage.py` | 设备用途、层级、旋转属性、协议和传输方式分开；前端不再关联 SCSI host 或解读设备类别 |
| 三 CPU 能力 | `cpu.hpp`、parser/cpu、领域查询与序列化、`cpu.py` | 逐 CPU 事实与集合范围清晰；前端不再解释 SMT 或维护特性识别规则 |
| 四 采集选项 | 公共入口、请求元数据、filesystem/sensor reader、refresh/replay | 过滤可选择且可解释；回放不触发 I/O；默认策略与额外能力分别可验证 |
| 五 绑定与采集计划 | `bindings/pybind_sysal.cpp`、`collector.py`、`_native.pyi`、新增 Python 计划模块 | 卡片字符串不进入原生采集 API；绑定只做公共参数与数据转换 |
| 六 清理与文档 | 旧字段适配、两仓库契约文档和既有输出快照 | 语义实现唯一，旧数据缺失有明确处理，展示与库的选择相互独立 |

提交可独立阅读和验证。Sysal 独立示例直接使用公共模型与查询，
用于确认通用库的能力不依赖 Python。客户端切换后删除对应重复判断，避免长期双轨。

## 兼容与验收

- 原始值和来源继续保留，新增归一化结果不能覆盖或伪装原始证据。
- JSON 的新状态字段可缺失；读取旧数据时采用明确的未知状态，不依据当前主机补全历史数据。
- 枚举值保持既有编号稳定；旧字段的保留、弃用和移除分别说明，破坏性变更随库版本明确交付。
- Sysal 与 SystemCard 分别提交、验证和版本化。客户端通过正式版本及 SHA-256 固定依赖，
  仅在库接口完成后更新固定版本，不添加本地覆盖路径。
- 保持 C++20、Python 3.6.8 运行兼容、CentOS 7/glibc 2.17 产物要求，以及只读采集。
- 迁移优先验证零设备、部分枚举、可选属性缺失、旋转属性未知、光驱与磁盘、混合 CPU 能力、
  策略跳过、刷新复用选项，以及带新旧字段的 JSON 往返。
- 按当前项目约定使用必要构建、静态检查、真实采集和独立故障样本；不新增或本地运行单元测试。
  既有 CI 和兼容 wheel 验证继续执行。
- 迁移期间 SystemCard 0.1.2 保持未发布，完成职责切换与实际展示验收后再安排发布。

本契约覆盖现有采集能力和模型。GPU、软件或其他硬件检测范围的扩展另行规划。
