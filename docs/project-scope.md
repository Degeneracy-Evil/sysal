# Sysal / SystemCard 项目边界

## 定位

Sysal 提供有来源、语义明确的系统资源事实，说明机器拥有的资源以及当前进程能使用的资源。
维持强类型模型、按域采集、部分失败降级、原始证据和 JSON 能力。

SystemCard 帮助用户快速读懂机器配置和进程资源限制。概要便于扫读，普通详情便于查阅，
诊断与拓扑按明确请求展开。一个字段进入 Sysal 模型后，是否进入界面仍需单独判断。

已有详细库存保留。当前优先维护采集可靠性、数据语义、展示和代码结构；
暂停扩展 NUMA 距离、总线/端口细节及更多设备检测。GPU 和软件检测维持既有范围。

## 视图与采集

| 入口 | 回答的问题 | 内容 |
| --- | --- | --- |
| 默认概要 | 系统各域提供了哪些信息 | 全部栏目概要，包括软件、传感器、健康证据和拓扑；不展开完整明细 |
| 普通详情 | 部件身份和主要配置是什么 | CPU 核心/缓存/频率、DIMM 配置、磁盘身份和块设备挂载、网卡身份和链路 |
| topology | 系统明确报告了哪些设备关系 | NUMA、PCI、EDAC、RDMA、存储控制器/协议、块设备/接口依赖、完整挂载 |
| sensors | 传感器报告了什么 | 原始读数、单位、限值和驱动标志 |
| health | 有哪些健康证据与查询结果 | 传感器、RAID、EDAC、只读 SMART/NVMe 报告，当前与历史证据分开 |
| software | 系统报告了哪些软件环境 | 既有软件栈查询 |
| --sources | 数据来自哪里，为何缺失 | 各域来源、采集状态和实际观察到的失败原因 |

SystemCard 默认展示全部栏目概要，并采集 Software、Sensors、StorageHealth。
compact 仅展示四个核心栏目，不请求这三个域；指定 section 时只采集所需域与依赖。
普通 storage 详情只请求 Storage；health 承担完整设备健康查询。
按域采集允许必要的辅助读取，不承诺某个域内部只读取界面展示的字段。
Sysal `System::collect()` 的默认范围仍为 `sysal::full`；库调用方自行选择范围。

## 数据语义

- 未知、失败、未采集与有效零值分别表达。成功的空库存可以显示零设备；
  缺少采集状态的旧空快照保持未知。失败域不能把默认空模型显示成成功的零库存。
- 整盘容量只汇总整盘，避免重复累计分区和虚拟层。全部未知时显示未知；
  部分已知时明确标注已知部分。有效零容量保留。
- 域成功表示该域生成了结果，不保证每个字段或设备完整。`meta.observations` 保留来源状态。
- `Memory.dimm_count` 是当前来源观察到的 DIMM 条目数；固件报告数量由 `reported_slot_count`
  表达。EDAC DIMM/rank 与固件条目保持各自的编号和匹配依据。
- 库存编号属于当前来源和快照，不替代稳定设备身份。当前速率、硬件上限、策略上限分别呈现。
  累计错误计数不等于当前故障；没有健康发现不等于机器健康。
- JSON 无符号编号、容量和计数拒绝负数、小数、布尔和越界值；带符号温度保留负值。

## 代码职责

Reader 读取原始证据；Parser 解析本域事实；Resolver 负责跨域关联和可见性；
Serialization 按领域处理 JSON，顶层仅组装 System/Meta/RawStore。

SystemCard 的领域模块构建卡片，model 负责选栏和组合，renderer 负责宽度适配。
资源限制格式由独立小模块共享。协议、挂载等专项表格可复用，避免复制领域解释逻辑。
不引入通用反射、模板生成框架或复杂的采集参数体系。

`System` 是可修改的采集快照，公开成员和 `refresh()` 都可以改变对象。
共享快照只有在没有并发修改时才可并发读取；修改和刷新由调用方同步。

## 后续工作原则

先依据用户问题决定视图和采集范围，再考虑新增字段。代码整理按职责和依赖进行，
文件长度仅用于定位阅读负担。公共模型和有效旧 JSON 保持兼容。

当前不新增或本地运行单元测试。结构迁移使用必要构建、真实采集、JSON 往返及终端预览验证。
后续补测试优先使用独立输入、真实故障样本和兼容问题，避免照着实现复述断言。
开发记录保留在 Git 提交中。
